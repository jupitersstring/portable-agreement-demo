Portable agreements: try it, verify it, extend it

Working developer prototype · 25 October 2026 · standalone browser demonstration

What was built

Try the browser demonstration · Public source repository

A working, browser-only demonstration of an agent hiring another agent for a research report. It uses real Ed25519 signatures and the existing portable work-order /0.3 byte framing. The visitor controls both synthetic roles. It does not run a model or move money.

Run locally

Extract the package, open a terminal in this folder and run:

python3 run_demo.py

Open the localhost address printed in the terminal. Python uses only its standard library. There is no package installation or service account. If the default port is busy:

python3 run_demo.py --port 0

The app needs JavaScript and WebCrypto Ed25519 in a browser with a secure context: HTTPS or localhost. Opening index.html directly as a file is not the supported launch path. Ctrl+C stops the launcher.

The demonstration

  1. Create the offer at 90 demo credits. Only the customer has signed; it is a proposal.
  2. Review the exact work, price and deadline. Accept as the provider. Both keys now approve the same fingerprint.
  3. Try changing the signed price. Altering the terms breaks the fingerprint; replacing the fingerprint still leaves invalid old signatures.
  4. Change the price to 130 and propose a revision. The old record remains at 90. The new proposal needs fresh provider acceptance.
  5. Record the incomplete report and a dispute. The record preserves who claimed what and its evidence hash. It does not decide quality or appoint an arbitrator.
  6. Prepare and download the JSON. Open another tab and import it, optionally pinning its fingerprint obtained separately. It verifies without the original signing keys.

New demo creates new temporary keys and a fresh offer. Undo restores one previous local session after reset or import. Reloading or closing the tab does not persist its keys. Imported records are read-only unless the same tab still holds the matching original keys.

Verify outside the interface

With a Node.js runtime supporting WebCrypto Ed25519, use the independent command-line verifier:

node verify_record.mjs evidence/browser-export.json 0c5e237c3a6b8d9c9d7411accdd2b6c54169c104875fb3722b9dee6cd76fd12f

A valid result reports accepted signatures and ordered event links. Payment and quality remain false. A changed record or wrong pin exits with a refusal. The sample above is public synthetic test data, not a credential.

Publish the demonstration

Deploy only the contents of site/ to an HTTPS static host that serves .mjs files as JavaScript. There is no build step, backend, private configuration or secret key to upload. Keep all four assets together. The root must serve index.html.

The app carries a restrictive content-security-policy meta tag, including no application network connections. For deployment, also set HTTP headers: Content-Security-Policy with frame-ancestors 'none', X-Content-Type-Options: nosniff and Referrer-Policy: no-referrer. The local launcher already sends these. A hosting provider may keep ordinary request logs; the application itself has no analytics or telemetry.

Before sharing, test the deployed HTTPS URL from a clean browser: sign, revise, export, and verify the downloaded file separately. Confirm its response headers and .mjs MIME types. The initial local build performed no public deployment or repository push. This public repository contains the standalone demo snapshot; no HN submission or production-network launch is part of publishing it.

What lies beyond this example

The useful core is a portable commitment: exact terms, explicit assent, links to evidence and a record that survives moving between tools. Broader SDK modules provide configurable building blocks; they are not all features of this small browser app.

CapabilityPractical useBoundary
Owner control and delegationLet an agent negotiate within an owner's budget and scope, while reserving final acceptance or sensitive actions for the owner.Signatures require an adopted identity, authority and key-management arrangement. A draft is not owner permission.
Complex contractingCompose milestones, nested obligations, subcontractors, guarantors, conditions and agreed changes.Exact meanings and who must assent remain explicit. Arbitrary prose does not become executable law.
Markets and exchangeBuild listings, bids, escrow, auctions, credit or resource exchanges around adopted market rules.Real custody and settlement depend on actual providers and separately authorised execution. The demo has only synthetic credits.
Dispute proceduresAgree evidence standards, panels, staged decisions, appeals and remedies before a disagreement arises.Decision-makers must be appointed and trusted for that role. An award is not automatic recognition or enforcement by a court.
Privacy and proofsCarry encrypted evidence or scoped disclosures, and adopt verifiers for particular cryptographic statements.Choose keys, recipients, circuits or verifier assumptions explicitly. Hashing is not encryption; disclosure cannot be recalled.
Discovery and reputationFind agents, mechanisms or services using contextual evidence and graph-based ranking.A score is evidence for a particular purpose, not universal trust or proof of independent control.
InteroperabilityAttach commitments to MCP tools, A2A tasks and other adopted services without forcing every participant onto one platform.Transporting a message does not itself prove acceptance, authority or payment. Each adapter needs its own compatibility and execution checks.
Offline operationSign and carry records by files, QR or store-and-forward carriers, then verify later.This web app does not implement physical radio, Bluetooth or a service-worker cache. Offline signatures cannot guarantee against double spending.
Optional shared ledgerAdd agreed ordering, replicated history or anchoring when independent participants need a shared view.The portable record does not require a blockchain. Validator operation, consensus security, finality and production deployment are separate work.

Security and meaning

Signing proves that a key approved exact bytes. It does not establish a real-world identity, legal enforceability, report quality, funds movement, completeness of history or the latest agreement. Revisions link their parent but do not silently release earlier obligations.

Exports always contain the work terms, public keys, signatures and event hashes. Evidence text is off by default and requires explicit inclusion. Exported terms may themselves be sensitive. Predictable content can sometimes be guessed from its hash. This demo does not encrypt exports.

The two private keys are non-extractable browser CryptoKeys and live only in memory. They are absent from JSON, browser storage and the server. A compromised browser or modified hosting JavaScript remains outside these checks. Use synthetic data in this demonstration.

The browser verifier is deliberately narrow: portable work-order /0.3, printable ASCII signed terms, bounded exact integers, SHA-256 domain-separated identifiers and strict WebCrypto Ed25519 verification. Evidence text may be UTF-8. This is not a complete verifier for every historical SDK profile or signature-admission rule.
